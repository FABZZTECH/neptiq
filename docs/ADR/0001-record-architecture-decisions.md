# ADR 0001 — Record architecture decisions

- **Status:** Accepted
- **Date:** 2026-08-28
- **Supersedes:** none

## Context

CONSTITUTION.md §9 (§8 at the time this ADR was written; renumbered when
§8 AGENT AUTHORITY AND ITS LIMITS was inserted — see ADR 0001 entry 7)
states: *"This document changes only by an ADR in
`docs/ADR/` explaining what changed, why, and what evidence prompted it.
Silent edits are a process violation."* ARCHITECTURE.md is likewise
*"authoritative on structure, stack, and invariants"*, and CONSTITUTION §5 P12
and the preamble both require that a disagreement with a governing principle be
*raised as an ADR rather than worked around*.

Until this record exists there is nowhere for such a decision to live, which
means the only available options are silent deviation (a process violation) or
inaction. This ADR establishes the register.

## Decision

1. Every deviation from CONSTITUTION.md or ARCHITECTURE.md is recorded as a
   numbered file in `docs/ADR/`, before or with the change that deviates.
2. An ADR states: context, the decision, the alternatives rejected, the
   consequences, and — per CONSTITUTION §9 — **the evidence that prompted it**.
   "It was easier" is not evidence.
3. ADRs are immutable once accepted. A later decision *supersedes* an earlier
   one by referencing it; the earlier file is not edited. This mirrors
   CONSTITUTION P4 (correction by superseding, never by mutation) applied to
   our own process.
4. Numbering is sequential and gapless. `0001` is this file.
5. Amending CONSTITUTION.md or ARCHITECTURE.md itself requires an ADR that
   quotes the previous text verbatim, so the diff is auditable from the ADR
   alone.

## Alternatives rejected

- **Git history as the record.** A commit message explains *what* changed, and
  reviewers reliably fail to reconstruct *why* six months later. CONSTITUTION
  §9 asks for reasoning and evidence, which a diff does not carry.
- **A single running DECISIONS.md.** Mutable, so it violates the same
  append-only discipline the product enforces on its own data. It also produces
  merge conflicts on every parallel decision.

## Consequences

- A pull request that deviates from the governing documents without an ADR is
  rejected on process grounds, independent of code quality.
- The ADR directory is the first place to look when a reader asks why the code
  disagrees with ARCHITECTURE.md.

| 14 | **Task 2B-1 step 4: the composite membership-JOIN-organizations failure (entry 6's / the prior commit's "not yet diagnosed" defect) was root-caused with a scripted repro, and the named hypothesis was refuted, not confirmed.** The hypothesis under test was: "the `organizations` policy's EXISTS subquery over `memberships` re-enters the `memberships` RLS policy and evaluates false under a `user_id`-only binding." A Python script (`asyncpg`, connecting as `neptiq_app` against a scratch DB seeded with one user/org/membership row, migrated via the real `alembic upgrade head`) ran the composite query, the bare EXISTS clause standing alone, and the standalone `memberships` SELECT, each inside one transaction with `set_config('neptiq.user_id', ..., true)` executed first — **every one of these returned the seeded row correctly.** `EXPLAIN (ANALYZE, VERBOSE)` of the composite JOIN confirms the RLS quals attach and evaluate as designed, including the nested `SubPlan` re-entering `memberships`' own policy from inside `organizations`' EXISTS clause. A second script ran the actual production call path — `neptiq_db.session.identity_session` plus the literal SQLAlchemy query from `get_tenant_context` — and it also resolved correctly. **Actual mechanism, confirmed by direct reproduction:** `set_config(key, value, true)` (`is_local => true`) scopes the GUC to the *current transaction*, not the current *connection* or *session*. The prior session's manual psql testing bound the GUC and ran the dependent query as what were, or could easily have been, two separate transactions (separate `psql -c` invocations = separate connections entirely; or the same connection in autocommit mode, where every statement is its own implicit transaction) — reproduced directly: `set_config` in one autocommit statement, then `current_setting('neptiq.user_id', true)` in the next, returns `NULL`, and the dependent query then returns zero rows, exactly matching the originally observed symptom. Wrapping both statements in one explicit `BEGIN`/`COMMIT` (or one `session.begin()` block, which is what `identity_session` and `tenant_session` both already do) makes the binding visible to the query and the composite lookup succeeds. **Conclusion: no RLS policy defect exists in `memberships.sql` or `organizations.sql`; the prior "zero rows" observation was an artefact of how the manual psql verification was structured, not of the policy SQL or of `identity_session`'s implementation** — `identity_session` already binds and queries inside one `session.begin()` block (see `neptiq_db/session.py`), so the production code path was never actually at risk; only the manual verification method was. Verified by: `db/repro_task1.py` and `db/repro_task1_orm.py` (both run against a real PostgreSQL 18 scratch database migrated via `alembic upgrade head`, output captured in the 2B-1 step 4 commit message; the scripts themselves were deleted after use as throwaway diagnostic scaffolding, not permanent artefacts — the durable record of this finding is this entry plus the `tests/integration/test_composite_membership_lookup.py` test landed in the same step, which pins the same scripted-transaction pattern as a regression test). | **Accepted** |
| 15 | **`identity_session` (added 2B-1 step 3, formalised here): a session bound to `user_id` only, with no `org_id`, for the one query that must run before an org is known.** Rationale: `get_tenant_context`'s bootstrap step resolves which org a user may act within — the org_id that every subsequent request binds — and that resolution cannot itself already know the org_id it is trying to discover. Binding no identity at all (`unscoped_session`) was tried first and found to be wrong (entry 6/13's originally-recorded defect): `memberships` is a tenant table under RLS, so a wholly-unbound session sees zero rows there once RLS is enabled, breaking every login. `identity_session` binds exactly `neptiq.user_id` via `set_config(key, value, true)` inside one `session.begin()` block — the same `is_local => true` transaction-scoping `tenant_session` uses, for the same reason (pooled-connection safety; see entry 14 for what happens when that scoping is NOT respected by the caller). **What it can read without a tenant binding, precisely:** exactly the rows `db/policies/memberships.sql` and `db/policies/organizations.sql` grant on a `user_id` match — a user's own membership rows, and organizations that user belongs to — and nothing else. Every other tenant table's policy compares only `org_id`, which is unbound under `identity_session`, so every other tenant table returns zero rows (fails closed) to a session opened this way; `tools/check_rls_coverage.py` (entry 16 dependency) verifies every `TENANT_TABLES` entry has such an org_id-only policy, so this closed-by-default property is mechanically checked, not merely asserted. `identity_session` has no write grant beyond what `WITH CHECK` allows: `memberships.sql`'s `WITH CHECK` clause is deliberately narrower than its `USING` clause (no `user_id` OR-branch), so this session can SELECT its own memberships but cannot INSERT or UPDATE one — granting memberships is a tenant-admin action gated by `Role`/`require_role` in the API layer, not by row visibility. Verified by: `tests/integration/test_identity_session.py` (org-membership resolution succeeds with `user_id` bound and no `org_id`) and the negative case in the same module (every other `TENANT_TABLES` table returns zero rows under an `identity_session`-bound connection). | **Accepted** |
